# UMI Database Setup

## Database policy

The application retains SQLite for local development and the existing unit tests. Production must use PostgreSQL, such as a Neon database. The existing `data/feedback_watch_tower.db` contains demo data and is intentionally **not** migrated. It remains preserved as a local reference and must not be deleted or overwritten.

Production receives a clean schema from Alembic and creates the standard handler seed records. No demo reporters, feedback, issues, events, notifications, or conversations are copied to Neon.

## Dependencies

The database dependencies are declared in `requirements.txt`:

- SQLAlchemy
- `psycopg[binary]` for PostgreSQL
- Alembic

Install them in the project environment with:

```powershell
pip install -r requirements.txt
```

## Environment variables

Copy `.env.example` to `.env` for local work. Do not put production credentials in a committed file.

```text
APP_ENV=development
DATABASE_URL=sqlite:///./data/feedback_watch_tower.db
CORS_ORIGINS=http://localhost:3000,http://127.0.0.1:3000
```

For an isolated PostgreSQL development database, set `DATABASE_URL` to the PostgreSQL URL supplied by the local server or a non-production Neon branch. Use a separate database for automated tests; never use the production database.

In Render, set `APP_ENV=production`, `DATABASE_URL` to the Neon connection string, and `CORS_ORIGINS` to the exact Vercel origin(s). The application does not silently switch a production configuration back to SQLite.

## Schema initialization

Apply the versioned schema from the project root:

```powershell
alembic upgrade head
```

Inspect the current revision:

```powershell
alembic current
```

Create a new migration after changing a model:

```powershell
alembic revision --autogenerate -m "describe the schema change"
```

Review autogenerated migrations manually before applying them. Do not use `Base.metadata.create_all()` as the production schema deployment mechanism.

The initial migration creates:

- `reporters`
- `feedbacks`
- `handlers`
- `issues`
- `events`
- `notifications`
- `conversations`

In development, application startup retains the existing SQLite `create_all()` behavior for convenience. In production, startup does not create or modify tables; run Alembic once as the Render release/pre-deploy command.

## Handler seeding

Development startup continues to seed the four default handlers when the handler table is empty. Production should run the same idempotent seed operation after migrations, rather than from every application worker:

```powershell
umienv\Scripts\python.exe -m app.seed
```

No demo feedback data is seeded.

## Testing

Run the existing SQLite regression suite:

```powershell
umienv\Scripts\python.exe -m pytest
```

For PostgreSQL validation, set `DATABASE_URL` to an isolated test database, apply `alembic upgrade head`, then run the same suite. Restore the environment to SQLite after testing:

```powershell
$env:DATABASE_URL = "postgresql+psycopg://user:password@localhost:5432/umi_test"
alembic upgrade head
umienv\Scripts\python.exe -m pytest
```

The PostgreSQL URL above is an example only. Do not commit credentials.

## Connection troubleshooting

- **`ModuleNotFoundError: psycopg`:** install the declared requirements in the active environment.
- **Connection refused:** verify PostgreSQL is running and the host/port are reachable.
- **Authentication failure:** verify the database user and password without printing the URL to logs.
- **SSL errors with Neon:** use the SSL parameters provided by Neon.
- **Missing tables:** run `alembic upgrade head` against the intended database.
- **Unexpected SQLite database:** inspect `APP_ENV` and `DATABASE_URL`; production must have an explicit PostgreSQL URL.
- **Wrong database target:** print only the database host/name from a reviewed local configuration, never secrets, and confirm the database is a dedicated development/test database.

## Data migration decision

The current SQLite records are demo data. No data transfer is required for the initial Neon setup. The SQLite database file remains intact, and the PostgreSQL database is initialized with schema and handler setup only.
